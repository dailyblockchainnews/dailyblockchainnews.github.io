LayerZero DVNs verify messages before delivery

What is a DVN in LayerZero? It verifies a source-chain message hash on the destination before an executor delivers it, using app-selected verifier requirements.

The Hashbeam Desk·Nov 25, 2026 · 05:11 UTC·3 min read

A DVN in LayerZero verifies that a message was sent on the source chain and attests to its payload hash on the destination chain before delivery. The destination chain cannot read Ethereum’s state directly, so independent verifiers check the source event and report their result to its endpoint.

What does a DVN verify in a cross-chain transfer?

A DVN verifies a message’s payload hash, which represents the message data, rather than delivering that message to the receiving application. In LayerZero V2, the app’s verification settings determine which DVNs must attest and how many optional DVN attestations are enough.

Take a USDC transfer from Ethereum to Berachain. The source application sends a message on Ethereum, and the DVNs assigned to that route wait for the configured Ethereum confirmations. Once they consider the message sufficiently confirmed, they attest to its hash on Berachain’s LayerZero endpoint.

The endpoint records those attestations against the message. The hash lets the destination verify that the message presented for delivery matches the one that was sent; the DVN’s role is to confirm and attest, not to carry out the token transfer.

How do required and optional DVNs affect verification?

Required DVNs must all verify the message, while optional DVNs count toward a threshold set by the application. Delivery can begin only after every required DVN and enough optional DVNs have verified.

That threshold provides a way to keep verification available when an optional DVN is offline. Say an app requires its designated DVN and sets a threshold across a group of optional DVNs. If one optional verifier stops responding, the message can still become verified when the required DVN and enough of the remaining optional verifiers attest. If a required DVN is unavailable, or too few optional DVNs respond to meet the threshold, verification remains incomplete and delivery cannot begin.

This is a configuration choice, not an automatic guarantee that every route has the same verifier set. The app chooses the required DVNs and optional threshold for its messages. For a user comparing a LayerZero message route with a Berachain bridge, the useful question is which verification design the route uses: the bridge moves assets across chains, while LayerZero’s DVNs attest to a cross-chain message before it can be delivered.

What happens after the DVNs verify the message?

After verification, a separate executor submits the destination delivery transaction and pays its gas. The DVN attests to the message hash; the executor calls the destination endpoint to deliver the verified message to the receiving application.

In the USDC case, the sequence is source message on Ethereum, confirmation and hash attestation by DVNs on Berachain, then delivery by the executor. The destination application can act on the message only after the verification conditions are met and the delivery transaction is submitted. That distinction matters: a verified message is eligible for delivery, but verification and execution are separate steps.

How did DVNs change LayerZero’s verification model?

LayerZero V2 introduced DVNs, replacing V1’s oracle-and-relayer model with configurable verifier networks and a separate executor role. In V2, the app’s verification configuration sets the conditions for attestation, while execution remains a distinct transaction.

In practical terms, a user tracking a Berachain bridge transfer can follow two milestones: the message becomes verified after the DVN requirements are met, then the executor delivers it on the destination chain. A delay before verification points to confirmations or missing attestations; a delay after verification is in the delivery step. The DVN confirms the message, and the executor delivers it.
