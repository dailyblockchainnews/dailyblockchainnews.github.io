Which RenBridge hashes show a transfer completed?

A deposit hash, RenVM hash and destination hash mark different stages; only the successful destination-chain transaction proves the asset arrived there.

The Hashbeam Desk·Nov 6, 2026 · 13:53 UTC·5 min read

A RenBridge transfer is complete on its destination chain only when the transaction that mints or releases the asset succeeds there. The source-chain hash proves that an input was submitted; RenVM’s transaction hash tracks protocol processing; neither alone proves the recipient received the output. RenBridge moves assets through these separate stages, so the useful evidence is a chain of records, not one magic hash. When checking a transfer, I use renbridge as the name of the flow, then match each identifier to its role.

Which RenBridge hash proves the deposit arrived?

The source-chain transaction hash identifies the deposit or burn that starts the transfer, and its chain record shows whether that input was included and confirmed. For a lock-and-mint transfer, this is the transaction that sends the supported asset to the Ren gateway address or calls the gateway contract. For a burn-and-release transfer, it is the transaction that burns the wrapped asset on the host chain and specifies the recipient on the release chain.

That hash establishes an input, not a completed bridge. A Bitcoin transaction can show funds sent to the gateway while the tokenized asset has not yet been minted. An EVM transaction can succeed while the burn event or intended recipient is not what the user expected. Check the transaction’s chain, status, asset, amount, gateway or contract, and relevant recipient details. A wallet’s “sent” label is not a substitute for the underlying chain record.

Ren’s Explorer support instructions accept the transaction hash for a deposit, the Ren deposit address, or the confirmed burn transaction hash to find the relevant transfer. Loading additional details can show whether the asset has arrived or remains pending. These are lookup keys; they are not equivalent completion proofs.

What does the RenBridge or RenVM hash establish?

The RenVM transaction hash identifies the protocol-side operation associated with the input. It lets a reader follow the operation through RenVM processing, including whether the required input confirmations have been observed and whether RenVM has completed its part. In a mint flow, RenVM validates the deposit and produces a signature authorizing the mint. In a release flow, it processes the burn and produces or submits the release to the source asset’s chain.

“RenVM done” is a stage marker, not a receipt on the destination chain. For a mint, the signature still has to be submitted in a mint transaction on the host chain; the user may need to sign and pay that chain’s transaction fee. If the interface stops after RenVM signs, the input may be recognized while the wrapped asset is still absent from the recipient’s balance.

Do not mistake protocol fields such as pHash or nHash for transaction hashes that independently prove settlement. They are values used in RenVM transaction data. An EVM transaction hash, a source-chain transaction ID, and a RenVM transaction identifier have different formats and refer to different records, even when an interface displays them together.

Which hash proves the asset reached its destination?

The destination-chain transaction hash is the decisive evidence for a completed mint or release. Open it on that chain’s explorer and verify that it is included with a successful status and that the resulting transfer or release matches the intended asset, amount, and recipient. For an EVM mint, inspect the token transfer or contract event as well as the transaction status: a successful contract call does not by itself establish that the expected token amount reached the expected address.

For an outbound mint, the evidence chain is therefore:

  • The source transaction shows the deposit at the gateway.
  • The RenVM record shows the operation was processed and signed.
  • The destination transaction shows a successful mint and the matching token transfer.

For a return transfer, reverse the roles: the host-chain burn hash proves the wrapped asset was burned; the RenVM record shows the burn was processed; the release-chain transaction hash proves the underlying asset was sent. A pending release or a burn alone does not establish that the recipient received funds.

How should a pending RenBridge transfer be checked?

Compare the records in stage order and stop at the first missing or mismatched step. Confirm that every explorer is showing the intended chain and that the transfer’s asset and recipient agree across records. If the source input is confirmed but there is no RenVM completion record, the bridge operation has not reached its output stage. If RenVM has signed a mint but no destination transaction exists, the mint submission may still be required. If the destination transaction exists but failed or sent a different asset or amount, its hash does not prove successful receipt.

Keep all three identifiers when asking for support: the source-chain hash, the RenVM transaction identifier, and the destination-chain hash if one was submitted. Include the gateway address for a deposit or the confirmed burn transaction for a release. This makes it possible to locate the operation and identify the stage that stopped.

The practical test is simple: the deposit hash proves the input, the RenVM hash proves protocol processing, and the successful destination-chain transaction proves delivery. Treat “complete” as a destination-chain result, then verify the recipient and asset in that result.
